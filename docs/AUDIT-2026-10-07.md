## High

**H1. The MCP `submit` tier can run arbitrary code (reproduced).**
- `aces_rod` runs every script of any `study_dir` under the MCP root (`domains/rod/route.py:118-153`). The script
  gets the server's full environment (line 141).
- An agent that can write a folder under the root can therefore run code as the server user. A planted
  `.git/config` `core.fsmonitor` would also run on every evidence record, because `evidence.py:37` calls
  `git describe`.
- **Fix:**
  - move `aces_rod` to the `full` tier, or allow only studies committed under `studies/`;
  - give stage scripts a minimal environment;
  - use an MCP root that excludes `src/` and `.git`.

**H2. `aces cost` gives wrong rankings for realistic inputs (D24 is proposed, not accepted). Block it for customer
use.**
- **Mass ignores material.** The part's mass is used for every material (`costing.py:308-317`). The example 1.2 kg
  aluminium-density part is priced as 316L at 1.2 kg (really about 3.6 kg) and ranked cheapest.
- **`--from-run` drops the operating conditions** (`from_pareto`, L262-273). A real 80 °C water design came back
  with PETG (rated 80 °C) as the top route.
- **Planned routes are recommended.** CNC and casting are marked `planned` (rule 13a), yet casting/316L is the
  first choice for a plate part at qty 1000. The test locks this in (`test_costing.py:39`).
- **Hard-coded material densities, prices and service temperatures** (rule 2). Silent defaults drive exclusions
  (25 °C, 1 bar, 1 mm feature, 0.3 mm tolerance: rule 1).
- **Arithmetic and validation errors:**
  - the LPBF build is shared as if three parts always fill it, even at qty 1;
  - casting labour is A$0;
  - tooling sets are not rounded up;
  - curves run past each route's quantity limit;
  - negative volume gives a negative cost; NaN mass counts as feasible;
  - several CLI inputs crash with a traceback.
- **Tests** check only ordering, with no hand-calculated cost (rule 15).
- **Fix** (costing agent):
  - take mass from the spec's material, with its source;
  - carry the conditions from the run's spec;
  - honour `aces.manufacturing` status;
  - validate inputs;
  - add hand-checked tests;
  - say "not a quote, not verified" in the output;
  - record D24–D26 in DECISIONS.md only once they are accepted.

**H3. CFD heat-transfer data can be filed under the wrong boundary condition (read + verified).**
- The CFD rows (`aces-tpms-periodic`) are H1, but carry no boundary field.
- `aces calibrate` defaults to `--boundary uniform_wall_temperature` (`cli.py:751`), and the README example leaves
  the flag out.
- Fitted that way, H1 data becomes Nu/3.66 labelled as uniform wall temperature. The mismatch check in `model.py`
  then passes, and designs get roughly 19 % more heat transfer under the label D11 calls conservative.
- **Fix:**
  - measurement rows carry `boundary`;
  - `calibrate` takes it from the rows and refuses mixed or mismatched rows;
  - decide (next free decision number) whether the design default stays uniform wall temperature (D11) or moves
    to H1 for conductive metal cores.

**H4. Developing laminar flow is treated as fully developed (verified).**
- `correlations.nusselt` returns laminar Nu 3.66/4.36 with `valid=True` whatever the length (`correlations.py:69-70`).
- In the hand-check case x* = L/(Dh·Re·Pr) is 0.030 (hot) and 0.022 (cold), well short of about 0.05.
  Hausen's mean Nu is 5.2 and 5.6, not 3.66, so the model under-predicts h by about 30–35 %. That is
  conservative, but it changes which designs win.
- The periodic CFD is thermally developed by construction, so calibration can't correct this.
- The docs say entrance effects are "stated on every result", but `ALWAYS_WARN` (`model.py:37-40`) doesn't include
  them.
- **Fix:** compute x* (Graetz number); warn, and use a developing-flow mean Nu (Shah & London / Hausen) when x* is
  below about 0.05. Make `ALWAYS_WARN` match ARCHITECTURE.md.

## Medium

**M1. Writes follow planted symlinks, and output-folder checks have a gap (reproduced).**
- The form route and formgen write with plain `open()`. Symlinks for `formgen.log` and the estimate JSON
  overwrote files outside the folder, and the run exited 0.
- Swapping the run folder for a symlink in the middle of a search sent all four run files outside the root.
- The same gap is in `stages.log`, `simlab.write`, `write_stl` and `Registry.save`. Windows junctions are not
  detected.
- **Fix:**
  - open the output directory once (`O_NOFOLLOW` / dir fd);
  - write files relative to it with `O_EXCL`;
  - require a new directory.

**M2. `export-simlab` trusts a ledger record without recomputing its hash (reproduced).**
- With `pareto.json` and its sha256 edited in the ledger, `verify` says BROKEN but export still succeeds
  (`cli.py:522-530`, `evidence.py:91`).
- **Fix:** recompute the record hash, and require `verify()` before export. Apply the same rule to
  `aces cost --from-run`.

**M3. Ledger integrity (reproduced).**
- A full rewrite with recomputed hashes passes `verify`, and so does cutting records off the end.
- A duplicate JSON key passes; a non-object line crashes `verify`.
- A half-written last line blocks every later append. A stale `.lock` blocks appends forever.
- `verify` reads without the lock.
- **Fix:**
  - anchor the head hash outside the file: a signed head, or one copied to the evidence engine;
  - reject duplicate keys;
  - type-check lines;
  - fsync appends;
  - use OS file locks, and lock in `verify`.

**M4. Registry hole (verified).**
- An entry with only `sources` loads as a calibrated factor of 1.0 with no valid range (`calibration.py:108`).
- It drops off the "uncalibrated" list and can never warn out of range.
- **Fix:** require `value`, a non-empty `valid_range` and `fitted_on` for any factor that has sources.

**M5. One MCP call can starve or exhaust the server (reproduced).**
- `_CLI_LOCK` is held for the whole run, and `stage_timeout_s` and the stage count have no limit.
- A read-tier call waited behind a rod run.
- Unclamped search bounds let a small `wall_ratio` push memory to GBs; at t/a 0.012 the peak was 2.5 GB.
- `aces_ledger_verify` reads whole files.
- **Fix:**
  - cap the timeout and the stage count;
  - clamp the bounds to each model's range;
  - limit read sizes;
  - run each CLI call in a subprocess with time and memory limits.

**M6. Dependency floors admit known-vulnerable versions** (pip-audit).
- `pillow>=10.0`: 34 advisories, fixed by 12.3.0.
- `mcp>=1.10`: 3 advisories, including DNS rebinding, which matters for the planned HTTP transport; fixed by
  1.28.1.
- `setuptools>=68`: 3 advisories.
- **Fix:** raise the floors, add PyNiteFEA to `requirements-formgen.txt`, and use hashes for the rig image build.

**M7. Process: no CI, and two agents push straight to `main`.**
- Commit `3d19b0f` ("test") is a broken placeholder on `main`: `costing.py` = `PLACEHOLDER_COSTING`, so the
  package can't import at that commit.
- Commit `00202af` is authored "Kimi (costing agent)" under Aaron's email.
- **Fix:**
  - a GitHub Actions workflow: pytest, ruff (selected rules), pip-audit;
  - agents push to branches and merge through PRs;
  - give each agent its own author identity.

**M8. The rig registry entry claims more than was verified (read).**
- `scripts/rig/register_solver.py:29` writes validation `status: "pass"`, although the rig GPU run is still pending
  (workstation GPU and rig CPU only).
- It registers the movable tag `aces-cfd:0.1`, not the image digest.
- **Fix:** status `pass-workstation; rig GPU pending`, and pin the digest.

## Code merged after `00202af` (HEAD `95be100`)

Three modules arrived while this audit ran: compliance (`0bfaa88`, pushed straight to `main`), the Isaac Sim tier
(PR #2) and the radar domain (PR #1). Two more reviews covered them: radar physics and code, and
compliance/Isaac security and licences. 219 tests collected, 219 pass. The findings carry an R (radar), C
(compliance) or I (Isaac) prefix.

**Verdict.** The radar equations that were hand-checked are right:

- range equation 2505 m;
- Albersheim 13.11 dB;
- Friis noise figure 2.76 dB;
- beamwidth, grating-lobe limit and patch resonance.

The plumbing around them is not ready. Two findings come before any other work: shell injection in compliance
(C1), and an Isaac validation case that cannot fail (I1).

### High

**C1. `aces compliance collect` runs shell commands built from user input (reproduced).**
- `compliance.py:198` runs `subprocess.run(c.command, shell=True)`. The command strings interpolate `--repo` and
  `--ledger`, so a value such as `x; id` runs its own command.
- The injected command's output is then hashed into the evidence manifest and chained into the ACES ledger, as
  if it were evidence.
- **Fix:** argument lists with `shell=False`; validate `--repo` as `owner/name` and `--ledger` as an existing file.

**C2. Secret-scanning evidence is collected with the secrets in it (read).**
- The GitHub secret-scanning alerts call does not pass `hide_secret=true`. Any live secret GitHub has found is
  written in plain text into the evidence folder, and from there into the auditor package.
- **Fix:** pass `hide_secret=true`, and test that no `secret` field reaches disk.

**I1. The Isaac free-fall validation can't fail (read; `adapter.py:188-205`).**
- The docstring promises the fall time within 5 % of √(2h/g). The code passes if the cube ended up lower than
  0.9 m and the analytic time (0.45 s) is shorter than the simulated window (600 × 1/60 = 10 s).
- It never measures a fall time. `converged` is hard-coded to 1.
- This is the record that would admit the solver to `solvers.json` (rule 3).
- **Fix:** record z(t), take the contact time, and pass only within 5 %. Derive `converged` from the run.

**R1. `aces design` crashes for every radar spec (reproduced).**
- The search runs and writes `pareto.json`. It then fails at `cli.py:482` (`model.resolution`: AttributeError);
  `cli.py:471` also assumes a `mass_kg` objective.
- So there is no `run.json`, no ledger record and no report. A radar design can't be exported, costed or claimed
  for R&DTI.
- **Fix:** make the domain contract explicit (resolution, mass key, warnings) and add a CLI test per domain.

**R2. Radar numbers that are wrong (read; each checked by hand).**
- No blind range: a monostatic pulse radar can't see closer than c·τ/2, and the model reports detection inside it.
- `calibrate.py:328` divides dB values as if they were linear ratios.
- The P1dB cascade (`cascade.py:173-177`) refers each stage's P1dB to the wrong gain.
- The phase-quantisation loss has the wrong sign (`array.py:74`, `:102`): coarser phase shifters show more gain.
- Duty-cycle clipping (`model.py:148`) lowers the reported transmit power and heat without saying so.
- The aperture check uses √area as if it were the width (`model.py:193`).
- Linear-array taper tables are applied to a planar array.
- No scan loss. Albersheim is used outside its fitted range. Coherent and non-coherent integration are mislabelled.
- **Fix:** a hand-calculated test for each item (rule 15); then refuse or warn outside each formula's range
  (rule 5).

### Medium

**R3. Unsourced defaults in radar (rules 1 and 2).**
- `model.py:73-79` holds default losses, noise temperature and efficiencies.
- `em_adapter` defaults the substrate to εr 3.66 with no source.
- **Fix:** move them to the spec with a `source` field, or refuse to run without them.

**R4. The radar EM adapter can report results it didn't compute (read).**
- The gprMax availability guard is broken, and `converged` is hard-coded.
- The Palace config it writes is empty.
- It reads the wrong S-parameter column.
- **Fix:** guard and test each solver path; take `converged` from the solver log.

**R5. Radar calibration is weaker than D18 and can't be reached.**
- `radar/calibrate.py` doesn't apply D18's rules: provenance, distinct conditions and held-out rows.
- No CLI command calls it.
- **Fix:** use the HX calibration path as the template, and add an `aces calibrate --domain radar` path.

**R6. Radar has no manufacturing route (rule 13a).** The radar template names none, and `aces.manufacturing` has
no PCB/antenna route. Add one (planned is fine) and require it.

**R7. MCP path check misses the radar calibration file (reproduced).** `SPEC_PATHS` doesn't list the radar spec's
`calibration_file`, so an MCP caller can point it at any file (`/etc/passwd` was accepted). Add it, and derive the
list from the spec models rather than a hand-kept table.

**R8 / I5. Export control and licences (rules 11 and 12).**
- Radar and C-UAS design data is the most likely DSGL item in the repo. AERIS data went through a GitHub PR, and
  nothing is classified.
- `docs/RADAR_EM.md` cites "decision 6" for a rule that isn't D6.
- Not in `LICENCES.md`:
  - Palace (Apache-2.0);
  - gprMax (GPL-3.0, so separate process only);
  - the GitHub CLI;
  - the NVIDIA Isaac Sim EULA. That licence is revocable, forbids redistribution, puts military use "at your own
    risk" and has an export clause.
- **Fix:**
  - **Aaron** classifies the radar work under DSGL;
  - get legal review of the Isaac EULA before any C-UAS/AERIS use;
  - add the four LICENCES entries before the next release.

**C3. Compliance `validate` and `index` only look at filenames (reproduced).** An empty file named
`A.8.15_log_2027-01-01.json`, dated in the future, counts as fresh, complete evidence. Check content, size,
hash and date against the run time.

**C4. Compliance writes follow symlinks, and the manifest can be overwritten** (as M1). Same fix as M1.

**I2. Isaac physics runs in FP32 (PhysX) and doesn't say so (rule 6).** That is acceptable for scene and robotics
checks, but not for verification. Label the solver FP32 in the registry, keep it out of `verification` runs, and
say so on every result.

**I3 / C5. Timeouts don't stop the work.** Timed-out Isaac and compliance runs kill only the shell, so the child
processes keep running. Start a process group and kill the group.
